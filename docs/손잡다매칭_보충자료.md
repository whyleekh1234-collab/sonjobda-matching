# 손잡다매칭 — 보충 자료

앞서 드린 「손잡다매칭 시스템 설명서」에 대한 검토 의견에 대해, **사실관계만** 보충한다. 법적 판단(침해 여부, 회피 가능성)은 하지 않는다.

---

## A. 사실 정정 — 인쇄물은 이미 서비스 안에 있다

> 검토 의견: "인쇄물은 현재 7개 분야에 없습니다. 소모품 공급이나 마케팅 대행 세부유형 어디에도 명시돼 있지 않습니다."

**사실과 다르다.** 인쇄물은 **소모품 공급 분야의 대표 항목**으로 처음부터 들어가 있다. 앞 문서가 7개 분야 이름만 적고 세부 항목을 생략해서 생긴 오해로 보인다. 실제 화면과 코드는 다음과 같다.

**1) 분야 설명 문구 자체에 있음** — 의뢰 등록 1단계 카드
```
소모품 공급 — "인쇄물/연구용 키트 등 소모품 공급업체 매칭"
```

**2) 의뢰 등록 시 고르는 세부 유형 (첫 번째 항목)**
```
인쇄물 제작 (ICF/CRF/라벨 등)
연구용 키트 (채혈/검체 등)
의료기기/소모품
기타
```

**3) 위탁업무 체크 목록 (첫 번째 항목)**
```
인쇄물 제작 (ICF/CRF/라벨/스티커 등)
연구용 키트 제작·조립
검체 운송 키트
보관·물류 (창고보관/온도관리)
배송 (실시기관 직접배송)
맞춤 제작·시제품
기타
```

**4) 파트너사 역량 프로필의 "공급 품목" 선택지**
```
인쇄물(ICF/CRF) · 라벨/포장 · 연구용 키트 · 검체 용기 · 의료 소모품 · 냉장/냉동 물류
```

**5) 납품 방식도 이미 입력받는다**: 실시기관 직접배송 / 의뢰사 일괄납품

→ 따라서 "사업모델에 넣으려면 분야 추가가 필요하다"는 전제는 성립하지 않는다. **이미 구현되어 운영 중**이다. 다만 "물품이냐 용역이냐"의 성질 판단은 여전히 남는 문제이므로, 위 항목들을 놓고 판단하시면 된다.

**참고 — 플랫폼이 관여하는 범위**: 인쇄물 건이라도 플랫폼은 "공급업체를 찾아 견적을 받는 것"까지만 한다. 주문·제작·배송·대금은 두 회사가 직접 한다. 플랫폼에 결제·배송 추적·재고 기능이 없다.

## B. 겸업의 정확한 경계

"CRO가 공급자이면서 동시에 수요자가 될 수 있는가"를 판단하려면, **어느 수준에서 동시인가**를 구분해야 한다. 시스템이 실제로 허용/차단하는 것은 다음과 같다.

| 상황 | 가능 여부 | 강제 위치 |
|---|---|---|
| 한 회사가 의뢰사 역할과 파트너사 역할을 **계정상 동시 보유** | **가능** (회원번호 SJ-CP-) | — |
| **같은 의뢰 건**에서 그 회사가 발주자이면서 견적 제출자 | **불가능** | 서버 함수가 거부: "자기 회사가 등록한 의뢰에는 견적을 낼 수 없습니다." |
| **같은 분야**에서 발주자이면서 수주자 (예: CRO 파트너사가 CRO 의뢰 등록) | **불가능** | DB 트리거가 거부 |
| **다른 분야**에서 발주자이면서 수주자 (예: CRO 파트너사가 SMO 의뢰 등록) | **가능** | — |

즉 현재 시스템에서 성립하는 겸업은 **"서로 다른 분야에서만"** 이다. 동일 분야·동일 거래에서 한 회사가 수요자이자 공급자가 되는 일은 발생할 수 없다.

선행특허 구성 7이 ①플랫폼 전체에서 한 주체가 양쪽 역할을 가질 수 있으면 충족되는 것인지, ②동일 거래(또는 동일 분야) 안에서 양쪽이어야 충족되는 것인지에 따라 판단이 갈릴 것으로 보인다. 이 구분을 청구항 원문에 대고 봐 주시기를 요청드린다.

### 현재 실제 데이터
운영 중인 회원 6명 중 겸업(SJ-CP-) 계정은 2개다. 테스트 목적으로 만든 것이고, 실제 외부 회원은 아직 받지 않았다(비공개 운영 중).

## C. 시스템이 실제로 강제하는 코드 (증거용)

화면 차원의 안내가 아니라 데이터베이스가 거부한다는 점을 보이기 위해 원문을 옮긴다.

**1) 같은 분야 의뢰 등록 차단** — `supabase/phase11_conflict_of_interest.sql`
```sql
create or replace function public.block_conflicting_request()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  if new.category = any (company_partner_categories(new.company_id)) then
    raise exception '귀사가 파트너사로 등록한 분야(%)의 의뢰는 등록할 수 없습니다.
                     이해상충 방지를 위한 조치입니다. (서비스운영정책 제3조)', new.category;
  end if;
  return new;
end;
$$;

create trigger requests_conflict_of_interest
  before insert or update of category, company_id on requests
  for each row execute function public.block_conflicting_request();
```

**2) 자기 회사 의뢰에 견적 금지** — `supabase/phase3_requests.sql`
```sql
if v_request.company_id = v_company_id then
  raise exception '자기 회사가 등록한 의뢰에는 견적을 낼 수 없습니다.';
end if;
```

**3) 한 회사당 한 의뢰에 견적 하나** — `supabase/schema.sql`
```sql
unique (request_id, company_id)   -- 한 회사가 한 의뢰에 견적 하나
```

**4) 매칭 전 의뢰사명 비공개** — `supabase/phase14_hide_client_name.sql`
회사 정보 조회 권한을 "내 회사 / 내 의뢰에 견적을 낸 파트너사 / 내 견적이 수락된 의뢰의 의뢰사 / 운영자"로 제한한다. 그 밖의 회사는 조회 자체가 되지 않는다.

| 날짜 | 내용 |
|---|---|
| 2026-09-19 | 이해상충 규칙(같은 분야 의뢰 등록 금지) 도입. 커밋 메시지에 도입 사유가 기록돼 있다 — "CRO가 의뢰사로 가짜 CRO 의뢰를 올리면 경쟁 CRO들의 견적가를 전부 볼 수 있다. 그걸 차단하기 위한 규칙이다." |

두 규칙 모두 **특허 회피가 아니라 거래 공정성·플랫폼 이탈 방지를 목적으로** 설계됐고, 그 목적이 도입 당시 기록에 남아 있다.

## E. 기술적으로 가능한 구조 변경 선택지

변리사께서 구조 변경이 필요하다고 판단하실 경우를 대비해, **개발 난이도만** 적어 둔다. 어느 것이 법적으로 의미 있는지는 판단하지 않는다.

| 선택지 | 개발 규모 | 사업 영향 |
|---|---|---|
| 겸업 자체를 금지(한 회사 = 한 역할) | 작음 (가입 화면 + 트리거) | 큼 — 정당한 겸업 수요를 막게 됨 |
| 의뢰사에도 회사유형을 받아 분리 (제약사·바이오벤처·의료기기·병원 등) | 중간 | 작음 — 오히려 파트너에게 정보 제공 |
| 분야를 물품(소모품·인쇄물)과 용역(CRO·SMO·RA 등)으로 상위 분류 | 중간 | 작음 |
| 특정 분야를 서비스에서 제외 | 작음 | 분야에 따라 다름 |
| 매칭 성사 처리(나머지 자동 미결정·자동 마감)를 수동으로 전환 | 작음 | 중간 — 사용성 저하 |
