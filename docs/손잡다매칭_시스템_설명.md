# 손잡다매칭 — 시스템 설명서

**목적**: 이 문서는 특허 침해·회피 검토, 법률 자문, 외부 설명을 위해 **실제로 구현되어 돌아가고 있는 것**만 적은 문서다. 계획·구상은 마지막 장에 따로 모았다. 화면 문구가 아니라 **서버(데이터베이스)가 강제하는 규칙**을 기준으로 적었다.

- 운영사: 주식회사 손잡다메디칼
- 서비스명: 손잡다매칭
- 형태: 웹 서비스 (PC·모바일 동일 주소, 반응형). 앱스토어 앱 없음.
- 현재 상태: 배포 완료, 접속 코드로 잠근 비공개 운영 중 (특허 출원 전)
- 기술: Next.js(웹) + Supabase(PostgreSQL). 접근 권한은 DB의 행 단위 보안(RLS)과 SECURITY DEFINER 함수로 강제된다.

---

## 1. 한 줄 정의

임상시험·바이오 업무를 **맡기려는 회사**와 **수행하는 회사**가, 서로의 신원을 모르는 상태에서 견적을 주고받고, 발주자가 하나를 수락하면 그때 서로를 알게 되는 B2B 매칭 플랫폼.

거래 자체(계약·대금)는 플랫폼 밖에서 두 회사가 직접 한다. 손잡다메디칼은 통신판매중개자이며 거래 당사자가 아니다.

## 2. 등장 주체

| 주체 | 설명 |
|---|---|
| **의뢰사** | 업무를 맡기는 회사. 의뢰(견적요청)를 등록한다. |
| **파트너사** | 업무를 수행하는 회사. 의뢰를 보고 견적을 제출한다. |
| **운영자** | 손잡다메디칼 직원. 가입 승인, 회원·분쟁 관리. 회원이 아니다(별도 번호 체계 SJ-ADMIN-). |

**중요 — 소유의 단위는 개인이 아니라 회사다.**
같은 사업자등록번호로 가입한 사람들은 하나의 회사로 묶이고, 의뢰·견적·매칭 이력을 공유한다. "한 회사는 한 의뢰에 견적 하나"가 DB 제약(unique)으로 걸려 있고, 담당자가 퇴사해도 의뢰·견적은 회사에 남는다(작성자만 익명 처리).

## 3. 전체 흐름

```
[가입] → [운영자 승인] → [의뢰 등록] → [해당 분야 파트너사에게만 공개]
   → [견적 제출] → [의뢰사가 열람·비교] → [하나 수락]
   → [매칭 성사: 나머지 자동 미결정 + 의뢰 마감 + 매칭번호 부여]
   → [수락된 두 회사에게만 상대 정보 공개] → [플랫폼 밖에서 직접 계약]
```

> **이 흐름 전체에 걸리는 제약**: 파트너사는 **자기가 등록한 분야에서는 의뢰사로 활동할 수 없다.**
> CRO 파트너사는 CRO 의뢰를 올릴 수 없고, 어떤 경우에도 자기 회사 의뢰에 견적을 낼 수 없다. (4장)

### 3.1 가입과 승인
- 사업자등록번호가 있는 법인·개인사업자만 가입 가능. 개인 불가.
- 가입 시 의뢰사 / 파트너사 / 둘 다(겸업) 중 선택.
- **가입 후 운영자 승인 전까지 로그인 자체가 거부된다** ("관리자 승인 대기 중입니다").
- 이미 등록된 회사에 합류하려면 **그 회사 담당 관리자가 발급한 초대 토큰**이 있어야 한다. 남의 사업자등록번호만 알아서는 그 회사에 들어갈 수 없다(가입 트리거가 토큰을 검사하고, 없으면 가입 자체가 취소된다). 초대는 지정 이메일 전용, 14일 만료, 1회용.
- 국세청 사업자등록 상태 조회 연동 코드는 완성돼 있고 API 키만 대기 중이다.

### 3.2 의뢰 등록 (의뢰사)
- 4단계 폼: 서비스 유형 → 프로젝트 정보 → 요구사항 → 검토·제출.
- 분야마다 묻는 항목이 다르다. 예) CRO는 적응증·임상단계(Phase I~IV, IIT, PMS, BE, RWE)·대상자 수·실시기관 수·모니터링 횟수·EDC, CMO는 제형·생산규모, 마케팅은 유형별 위탁업무 목록.
- 등록되면 고유번호(RQ-)가 붙고 **해당 분야 파트너사에게만** 노출된다.
- 매칭 성사 전까지 수정·회수 가능. 마감일 연장 가능.
- **자기가 파트너사로 등록한 분야의 의뢰는 등록할 수 없다.** 즉 파트너사는 자기 분야에서 의뢰사가 될 수 없다. 예: CRO 파트너사로 등록된 회사는 CRO 의뢰를 등록할 수 없고, SMO·RA 등 다른 분야 의뢰만 등록할 수 있다. 회사 단위로 적용되며, 화면에서 해당 분야 카드가 비활성 처리될 뿐 아니라 데이터베이스 트리거가 저장 자체를 거부한다. (근거·이유는 4장)

### 3.3 견적 제출 (파트너사)
- 자기 분야의 열린 의뢰에만 제출 가능. 마감된 의뢰에는 불가.
- **자기 회사가 등록한 의뢰에는 어떤 경우에도 견적을 낼 수 없다.** (겸업 회사 포함)
- 한 회사당 한 의뢰에 견적 하나(unique 제약). 같은 회사 동료가 이미 냈으면 그 견적을 이어서 수정한다.
- 금액·업무범위별 소요기간·메모·첨부(견적서 파일, 필수).
- **의뢰사가 그 견적을 열람하기 전까지만** 수정·회수 가능. 열람 후에는 잠긴다.
- **파트너사는 다른 파트너사의 견적을 볼 수 없다.** 의뢰사만 자기 의뢰에 온 전체 견적을 본다.

### 3.4 수락과 매칭 성사
의뢰사가 받은 견적 중 하나에서 "견적 수락"을 누르면, 서버 함수가 **한 트랜잭션으로** 다음을 처리한다. 중간에 끊겨 일부만 반영되는 일이 없다.

1. 호출자가 그 의뢰의 소유 회사인지 확인 (아니면 거부)
2. 의뢰가 아직 진행중(pending)인지 확인 (이미 마감이면 거부)
3. 수락한 견적 → `accepted`
4. 같은 의뢰의 나머지 견적 → `not_selected`(미결정)
5. 의뢰 → `matched`(마감)
6. 매칭 관리번호(MT-) 부여

수락은 되돌릴 수 없다. 별도의 상대방 동의·승낙 절차는 없다 — 의뢰사의 수락 행위 하나로 매칭이 성립한다.

### 3.5 연락처 공개 절차

**언제**: 위 수락 트랜잭션이 끝난 시점부터. 별도의 공개 신청이나 운영자 승인이 없다.

**누구에게**: 그 의뢰의 의뢰사 ↔ 수락된 견적의 파트너사, 두 회사에만. 같은 의뢰에 견적을 냈지만 선택되지 않은 파트너사에게는 아무것도 공개되지 않는다.

**무엇이**: 회사명, 회사 로고, **담당자명, 이메일, 전화번호**

**누구의 연락처인가** — 회사 구성원 전체가 아니다.
- 의뢰사 쪽: **그 의뢰를 등록한 담당자**
- 파트너사 쪽: **그 견적을 마지막으로 제출·수정한 담당자**

**어떻게 열리는가**: 전용 서버 함수(`get_match_contacts`) 하나로만 조회된다. 이 함수는 호출될 때마다 다음 네 가지를 순서대로 확인하고, 하나라도 어긋나면 값을 주지 않고 거부한다.

1. 그 의뢰가 존재하는가
2. 의뢰 상태가 `matched` 또는 `completed`인가 → 아니면 "매칭이 성사된 뒤에 공개됩니다"
3. 수락된 견적이 실제로 있는가 → 없으면 "수락된 견적이 없습니다"
4. 호출자의 소속 회사가 **그 의뢰사이거나 그 수락된 파트너사**인가 → 아니면 "이 매칭의 당사자가 아닙니다"

통과한 경우에만 양쪽 담당자 정보를 돌려준다. 화면에서 가려 두는 방식이 아니라 **서버가 값을 내주지 않는 방식**이므로, 제3자가 API를 직접 호출해도 얻을 수 없다.

회사명은 이와 별도로 회사 조회 권한(RLS)에서도 열린다. 매칭 전 파트너사에게 의뢰사 회사명이 보이지 않던 것이, 매칭 후 그 파트너사에게만 보이게 된다.

**어디에 표시되는가**
- 의뢰사: 대시보드 "매칭 성사" 탭의 해당 의뢰 카드 안
- 파트너사: 대시보드 "매칭 성사" 탭의 해당 건 안
- 문구: "매칭 성사로 (상대) 연락처가 공개되었습니다" + 회사명·담당자명·이메일·연락처

**현재 동작상 유의점 (사실 그대로 적는다)**
- **매칭 성사 시 상대방에게 알림 메일·문자가 자동 발송되지 않는다.** 파트너사는 자기 대시보드에 들어와야 수락된 사실과 연락처를 알 수 있다.
- 연락처의 출처가 "그 의뢰를 등록한 담당자 / 그 견적을 낸 담당자"이므로, 그 담당자가 탈퇴한 뒤에는 해당 쪽 연락처가 표시되지 않는다(회사에는 의뢰·견적이 남지만 작성자 연결이 끊기기 때문).

### 3.6 정보 공개 시점 요약

| 정보 | 매칭 전 | 매칭 후 |
|---|---|---|
| 의뢰 내용(분야·규모·예산·마감) | 해당 분야 파트너사에게 공개 | 공개 |
| **의뢰사 회사명** | **비공개** — 파트너사 화면에 "의뢰사 비공개"로 표시 | 수락된 파트너사에게만 공개 |
| 파트너사 회사명·역량 프로필 | 견적을 받은 의뢰사에게 공개 | 공개 |
| **담당자명·이메일·연락처** | **양쪽 모두 비공개** | 수락된 양자 간에만 공개 |
| 다른 파트너사의 견적 내용·금액 | 서로 비공개 (의뢰사만 전체 열람) | 서로 비공개 |
| 탈락한 파트너사 | — | 아무것도 공개되지 않음 |

의뢰사명을 매칭 전까지 가리는 이유는 **플랫폼 밖에서 개별 연락해 거래하는 것을 막기 위함**이다. 화면에서 숨기는 수준이 아니라 회사 조회 권한 자체를 제한해서, API를 직접 호출해도 그 회사 행이 나오지 않는다.

## 4. 이해상충 방지 규칙 ★

> 이 장은 "한 회사가 의뢰사이면서 동시에 파트너사일 수 있는가"라는 질문과 직접 관련된다.

### 4.1 겸업은 허용한다
한 회사가 의뢰사와 파트너사 역할을 **동시에 가질 수 있다.** 실제로 중견 CRO가 통계·데이터관리를 외주 주면서 임상 운영은 수주하는 일, CMO가 인허가 컨설팅을 의뢰하는 일이 흔하기 때문이다.

### 4.2 대신 "같은 분야"를 막는다
**파트너사로 등록한 분야와 같은 분야의 의뢰는 등록할 수 없다.**

- 예: CRO 파트너사로 등록된 회사는 **CRO 의뢰를 등록할 수 없다.** SMO·RA 등 다른 분야 의뢰는 등록할 수 있다.
- 반대 방향도 막는다: 특정 분야 의뢰를 진행 중인 회사는 그 의뢰가 마감·회수되기 전까지 그 분야를 파트너 분야로 **추가할 수 없다.**
- 이 제한은 **회사 단위**로 적용된다. 같은 회사의 어느 멤버가 등록한 분야든 회사 전체에 미친다.
- 화면에서는 해당 분야 카드가 비활성 처리되고, 누르면 사유가 안내된다. 강제는 DB 트리거가 한다(화면을 우회해도 거부).

막는 이유: CRO가 의뢰사 행세로 가짜 CRO 의뢰를 올리면 **경쟁 CRO들의 견적 금액을 전부 열람**할 수 있게 된다. 그걸 차단하기 위한 규칙이다.

### 4.3 그 밖의 금지
- 어떤 경우에도 **자기 회사가 등록한 의뢰에는 견적을 제출할 수 없다.**
- 사실상 같은 회사가 별도 사업자등록번호로 계정을 나눠 위 제한을 우회하는 행위는 이용 제한 사유.
- 이용 제한은 경고 → 일시 제한 → 이용 정지 순. **누적 3회 이상이면 영구 탈퇴**(해당 사업자번호 재가입 불가). 사업자번호 도용·비공개 정보 부정 접근 등 중대 위반은 즉시.

## 5. 데이터 구조 요약

| 테이블 | 내용 |
|---|---|
| companies | 회사 (사업자등록번호 unique, 회사명, 주소, 로고) |
| profiles | 회원 (회사 소속, 역할 배열, 파트너 분야 배열, 승인 상태) |
| company_invites | 회사 합류 초대 토큰 |
| requests | 의뢰 (회사 소유, 분야, 분야별 상세는 JSON) |
| quotes | 견적 (회사 소유, **(의뢰, 회사) 조합 unique**, 금액·기간·첨부) |
| partner_profiles | 파트너사 역량 (회사 단위, 질환영역·단계·지역·규모·인증·실적 + 분야별 항목) |
| company_change_requests | 회사 정보 변경 요청·승인 이력 |
| notifications / notices / inquiries | 알림·공지·문의 |

**번호 체계**: 회원 SJ-C-(의뢰사) / SJ-P-(파트너사) / SJ-CP-(겸업) / SJ-ADMIN-(운영자), 의뢰 RQ-, 견적 QT-, 매칭 MT-, 알림 NF-

**견적 상태**: 임시저장 → 제출 → (의뢰사)검토중 → 수락 / 거절 / 보류 / 미결정
**의뢰 상태**: 진행중 → 매칭성사 → 완료, 또는 회수

## 6. 부가 기능 (구현됨)

- **파트너사 역량 프로필**: 회사 단위로 전문 질환영역·경험 단계·수행 지역·직원 수·연간 과제 수·인증·대표 실적 + 분야별 항목(CRO는 CRA 수·협력기관 수·제공 서비스, CMO는 제형·생산규모 등)을 등록. 의뢰사가 견적을 비교할 때 견적 옆에 함께 보인다. 운영자가 "확인" 표시를 할 수 있고, 내용이 바뀌면 확인 표시는 자동 해제된다.
- **회사 로고**(선택): 가입 시 또는 마이페이지에서 업로드. 견적 카드·상단 바 등에 표시.
- **AI 상담 챗봇**: 서비스 이용 안내 전용. 가입·견적·매칭 규칙을 답한다. 특정 회원의 진행 상황이나 법률 자문은 다루지 않고 문의하기로 넘긴다. (Claude API 사용)
- **회사 정보 변경 요청·승인**: 회사명·사업자번호·주소는 회원이 직접 못 바꾼다. 담당 관리자가 요청하면 운영자가 승인해야 반영된다.
- **관리자 기능**: 회원 승인·제한·정지·삭제, 회원/회사 정보 직접 수정, 의뢰·견적·매칭 전체 조회, 첨부 견적서 열람, 문의 답변, 공지·알림 발송.
- **홈 화면 추가(PWA)**: 모바일에서 앱처럼 실행 가능.

## 7. 하지 않는 것 (현재 범위 밖) ★

특허 검토 시 **경계**가 되는 항목이므로 분명히 적는다.

- **결제·에스크로 없음.** 대금이 플랫폼을 거치지 않는다. 결제 모듈 자체가 없다.
- **수수료 없음.** 현재 매칭 수수료를 받지 않는다(추후 정책 변경 가능, 변경 시 사전 공지).
- **자동 매칭·추천 알고리즘 없음.** 의뢰는 "해당 분야 파트너사 전체"에게 공개될 뿐, 시스템이 특정 파트너를 점수화해 추천하거나 자동 낙찰하지 않는다. 선택은 전적으로 의뢰사가 한다.
- **역경매·입찰 하향 경쟁 구조 아님.** 파트너사는 다른 파트너사의 견적을 볼 수 없으므로, 남의 금액을 보고 낮춰 부르는 구조가 성립하지 않는다.
- **계약서 작성·전자서명 없음.**
- **일정·산출물 관리(프로젝트 관리) 없음.** 매칭 성사 이후 진행은 플랫폼이 관여하지 않는다.
- **평점·리뷰 없음.**
- **물품 판매·재고·배송 처리 없음.** 소모품 공급(인쇄물 포함) 분야도 플랫폼이 하는 일은 "공급업체를 찾아 견적을 받는 것"까지다. 주문·제작·배송·대금은 두 회사가 직접 한다. 결제·배송추적·재고 기능이 없다.
- **개인(비사업자) 이용 불가.**
